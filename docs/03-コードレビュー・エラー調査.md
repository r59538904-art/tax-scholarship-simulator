## 障害1：住民税の年税額が公式計算例と100円ずれる（重大）

### 症状

```
【入力】給与収入 5,505,000円／名古屋市／夫婦＋子3人（19歳・16歳・12歳）
        社会保険料 825,600円／生命保険料（旧契約）80,000円

【期待】年税額 140,200円（名古屋市の公式計算例）
【実際】年税額 140,300円
```

初期の症状は「なんとなく数百円ずれる」で、単体の数値検証（税率表・控除額）ではすべて一致していたため、
原因が長く分からない類の不具合。

### 関連コード（修正前）

```js
/* assets/calc.js */
function salaryDeduction(income, p) {
  income = n(income);
  if (income <= 0) return 0;
  if (income <= p.salaryMinCap) return Math.min(income, p.salaryMin);
  if (income <= 3600000) return income * 0.3 + 80000;
  if (income <= 6600000) return income * 0.2 + 440000;   // ← ここ
  if (income <= 8500000) return income * 0.1 + 1100000;
  return 1950000;
}
// 呼び出し側
var salDed = salaryDeduction(salaryRev, p);
var salary = Math.max(0, salaryRev - salDed);
```

### 想定される原因（切り分けの順序）

| # | 仮説 | 検証結果 |
|---|---|---|
| 1 | 税率表が間違っている | ❌ 国税庁 No.2260 と完全一致 |
| 2 | 控除額が間違っている | ❌ 所得控除の合計 2,400,600円は公式例と一致 |
| 3 | 調整控除の計算が違う | ❌ 13,200円／3,300円で一致 |
| 4 | 100円未満切捨ての位置が違う | ❌ 市民税・県民税それぞれで正しく実施 |
| 5 | **課税標準額が1,000円ずれている** | ✅ 1,563,000円 vs 公式 1,562,000円 |
| 6 | **給与所得が800円ずれている** | ✅ **これが真因** |

### デバッグ手順（再現可能な手順として記録）

```bash
# 1. 公式計算例をそのまま入力する最小の再現コードを書く
node -e "
const C=require('./assets/calc.js'), D=require('./assets/data.js');
console.log('給与所得:', C.calcIncome(
  {income:{salary:5505000}, family:{}, carryover:{}},
  D.INCOME_TAX[2025], 'income').salaryIncome);
"
# → 3964000（公式例は 3963200）

# 2. 差分 800円 の出どころを探す
#    5,505,000 × 0.8 − 440,000 = 3,964,000
#    公式        　　　　　　　 = 3,963,200
#    差 800円 = 1,000円 × 0.8 → 収入側で 1,000円単位の丸めがある？

# 3. 4,000円単位で切り下げると一致するか試す
node -e "
const r=5505000, A=Math.floor(r/4/1000)*1000;
console.log('A =', A, '→', A*3.2-440000);
"
# → A = 1376000 → 3963200 ✅ 一致

# 4. 一次資料で規定を確認
#    所得税法別表第五「給与所得控除後の給与等の金額の表」
#    「その給与等の金額を4で除して千円未満の端数を切り捨てた金額をAとする」
```

### 真の原因

給与所得の金額は**率で直接計算するのではなく、所得税法別表第五の表で決まる**。
収入金額 1,900,000円超〜6,599,999円の区間では、

```
A ＝ 収入金額 ÷ 4 （千円未満切捨て）  ＝ 収入を4,000円単位に切り下げた額
給与所得 ＝ A × 2.8 − 80,000 （〜3,599,999円）
        ＝ A × 3.2 − 440,000 （3,600,000〜6,599,999円）
```

率で計算すると最大 3,199円 × 0.8 ＝ **2,559円** の誤差が出る。
これが課税標準額（1,000円未満切捨て）を最大2,000円ずらし、税額を数百円ずらしていた。

この不具合は **給与収入が4,000円の倍数だと発現しない**。
横浜市の公式例（5,500,000円＝4,000の倍数）では偶然一致していたため、
名古屋市の例（5,505,000円）を追加するまで検出できなかった。

### 修正方法

```js
/* 修正後：assets/calc.js */

/* 所得税法別表第五「給与所得控除後の給与等の金額の表」のとおりに計算する。
 * 収入が 190万円（令和8年分は220万円）を超え660万円未満の区間は、
 *   A ＝ 収入金額 ÷ 4（千円未満切捨て）
 * として A×2.8−80,000 / A×3.2−440,000 で求める。単純に率を掛けると
 * 最大で数百円ずれるため、この丸めを省略してはいけない。
 * （検証：名古屋市の公式計算例 給与収入5,505,000円 → 給与所得3,963,200円）
 */
function salaryIncomeAmount(revenue, p) {
  var r = Math.floor(n(revenue));
  if (r <= 0) return 0;
  if (r < p.salaryMinCap) return Math.max(0, r - p.salaryMin);
  var A = Math.floor(r / 4 / 1000) * 1000;              // 4で除して千円未満切捨て
  if (r < 3600000) return A * 2.8 - 80000;
  if (r < 6600000) return A * 3.2 - 440000;
  if (r < 8500000) return Math.floor(r * 0.9) - 1100000;
  return r - 1950000;
}
/* 表示用の給与所得控除額（収入 − 給与所得） */
function salaryDeduction(revenue, p) {
  var r = Math.floor(n(revenue));
  if (r <= 0) return 0;
  return r - salaryIncomeAmount(r, p);
}
```

あわせて `calcIncome()` の呼び出しを「所得を直接求め、控除額は差で表示する」順序に変更。

### 再発防止策

| 策 | 内容 | 実施 |
|---|---|---|
| **公式計算例を回帰テスト化** | 自治体が公開している計算例を、年税額まで1円単位で突合するテストにする | ✅ 横浜市・名古屋市の2例・27アサーション |
| **4,000円の倍数でない値を必ず含める** | 丸め不具合は倍数だと発現しないため、テスト値に非倍数を混ぜる | ✅ 5,505,000円・2,203,000円 |
| **境界値テスト** | 区分の境目（1,900,000／3,600,000／6,600,000／8,500,000円）で連続性を確認 | ✅ 11アサーション |
| **コメントで規定を明示** | 「単純に率を掛けてはいけない」理由をコード内に残す | ✅ |
| **一次資料の原文にあたる** | 解説サイトの「率の式」は簡略表現。法令・別表を確認する | ✅ 検証レポートに出典を記録 |

## 障害3：擬制世帯主の所得が国保の軽減判定から抜けていた

### 症状

世帯主が会社の健康保険に加入している世帯で、世帯主の所得が軽減判定所得に算入されず、
本来より軽い軽減割合が表示された（利用者に有利に誤る＝より危険な誤り）。

### 関連コード（修正前）

```js
['A','B'].forEach(function (w) {
  if (!meta[w].kokuho) return;   // ← 国保未加入なら所得も人数も一切カウントしない
  insured++;
  ...
});
```

### 真の仕様

国保の軽減判定所得は「**世帯主（擬制世帯主を含む）**＋被保険者＋特定同一世帯所属者」の合計。
世帯主が国保未加入でも**所得は含める**（ただし均等割の人数には入らない）。

### 修正方法

```js
var counted = meta[w].kokuho || head === w;      // 被保険者 または 世帯主（擬制世帯主）
if (meta[w].kokuho) insured++;                   // 人数は被保険者だけ
if (!counted) return;                            // 所得は世帯主も含める
```

STEP 7 に「世帯主はだれですか」の選択を追加し、`calcKokuho` に `includeSelf` を渡す設計に変更。

### 再発防止策

- **「有利側に誤る不具合」を優先的に洗い出す**方針を保守手順に追加
- 制度の主語（「世帯主」「被保険者」「特定同一世帯所属者」）を混同しないよう、
  変数名を `insured` / `head` / `tokutei` と明確に分けた

## 障害5：立場を「ひとり」に切り替えて戻すと配偶者が消えたままになる

### 症状

STEP 1 で「ひとりで使う」→「夫婦（2人）で使う」と戻すと、生計維持者Bの欄が復活しない。

### 関連コード（修正前）

```js
meta.B.enabled = mode() !== 'single' && ($('B_enabled') ? chk('B_enabled') : true);
```

`single` モードでは `B_enabled` 要素が存在せず `mode() !== 'single'` が false になるため、
`meta.B.enabled` が false で確定し、モードを戻しても false のまま復元されていた。

### 修正方法

「利用者の意思（`wanted`）」と「実際に計算に使うか（`enabled`）」を分離。

```js
// wanted … 利用者が「Bも計算する」と指定しているか（単身モードに切り替えても保持する）
// enabled … 実際に計算に使うか
if ($('B_enabled')) meta.B.wanted = chk('B_enabled');
meta.B.enabled = mode() !== 'single' && meta.B.wanted;
```

### 再発防止策

- **「表示状態」と「利用者の意思」を同じ変数で持たない**（UIの都合で意思が消える）
- モード往復のテストを追加

## 障害6：端数処理の誤り3件（`test/verify-calc.js` の新設で発見）

### 発見の経緯

「各関数を単独で、境界値と端数まで条文と突き合わせる」検証（`test/verify-calc.js`、306件）を
新設したところ、通しの計算例では表面化しない端数の誤りが3件見つかった。
期待値は実装から逆算せず、**条文・速算表から手計算した値を直書き**している。

### 症状と原因

| # | 箇所 | 誤 | 正 | 影響 |
|---|---|---|---|---|
| 6-1 | 公的年金等に係る雑所得 | 1円未満の端数が残る | 1円未満切捨て | **非課税判定が反転しうる** |
| 6-2 | 生命保険料控除・地震保険料控除 | 端数を切り捨て | 端数を切り上げ | 控除額が1円過少 |
| 6-3 | 山林所得の5分5乗 | 1/5にしたあと千円未満切捨て | 追加の切捨てをしない | 所得税額が最大数百円ずれる |

### 関連コード（修正前 → 修正後）

```js
// 6-1 calcIncome：速算表の結果は 収入×75% − 275,000 のように小数が出る
- var pension = Math.max(0, pos(inc.pension) - penDed);
+ var pension = Math.floor(Math.max(0, pos(inc.pension) - penDed));

// 6-2 steps()：国税庁「年末調整のしかた」は切上げと明記
- if (amount <= tbl.steps[i][0]) return Math.floor(amount * tbl.steps[i][1] + tbl.steps[i][2]);
+ if (amount <= tbl.steps[i][0]) return Math.ceil(amount * tbl.steps[i][1] + tbl.steps[i][2]);

// 6-3 calcIncomeTax：課税山林所得金額はすでに千円未満切捨て済み
- var fb = bracketTax(floorTo(tForest / D.FOREST.divisor, 1000));
+ var fb = bracketTax(tForest / D.FOREST.divisor);
```

### なぜ今まで気づかなかったか

- 6-1 は年金収入が4の倍数だと端数が出ない。公式計算例はきりのよい数字が多い
- 6-2 は保険料が偶数だと端数が出ない
- 6-3 は課税山林所得金額が5,000の倍数だと差が出ない

**「ふつうの入力では端数が出ない」場所こそ、意図的に端数の出る値で検証する必要がある。**

### 再発防止策

- `verify-calc.js` に、**端数が必ず出る値**（1,300,002円・20,001円・6,402,000円）を固定ケースとして常設
- 「合計所得金額・総所得金額等が整数であること」を不変条件として追加
- 新しい計算を足すときは、まず境界値と端数のテストを書いてから実装する

## 障害7：ダーク表示のまま印刷すると紙が黒くなる（新機能の実装中に発見）

### 症状

配色の切替を入れた直後、ダーク表示のままPDFに保存すると背景が暗いまま出力される。

### 原因

CSSの詳細度。印刷用の上書きが `:root`（0,1,0）なのに対し、
ダークの指定が `:root[data-theme="dark"]`（0,2,0）で、**後者が勝っていた**。
記述順は関係しない。

```css
@media print {
- :root { --bg: #fff; ... }
+ :root, :root[data-theme="dark"], :root[data-theme="light"] { --bg: #fff; ... }
}
```

### 再発防止策

`audit.js` D-4 に「印刷時はダークを上書きしていること」を静的チェックとして追加。
あわせて、ダークの色定義がメディアクエリ側と属性セレクタ側の2か所にある点も、
**キーと値が完全に一致すること**を機械的に突き合わせるようにした（片方だけ直す事故を防ぐ）。

## 障害8：国保の入力に「効かないほうの入口」が操作できてしまう（利用者からの指摘）

### 症状

国保の人数・所得を決める入口が2つあり、実際に使われるのは一方だけなのに、
**使われないほうも操作できてしまい、何の表示も出ない**。

| 入口 | 場所 |
|---|---|
| ① 加入チェック | STEP 3 の各世帯員「この人が国民健康保険の被保険者」 |
| ② 手動上書き | STEP 7 の「自動で数えた人数・所得を手動で上書きする」 |

そのため次の2つが起きていた。どちらもエラーが出ないため気づきにくい。

- 手動上書きON時：STEP 3 のチェックを入れ直しても**結果が1円も変わらない**
- 手動上書きOFF時：STEP 7 の数値欄に入力しても、次の再描画で**黙って書き戻される**

### 関連コード（修正前）

```js
// 自動計算中は、利用者が入力した値を毎回上書きしていた（案内も制御もなし）
if (!manual) {
  $('k_insured').value = k.insured;
  $('k_salary').value = k.earners;
  $('k_other').value = Math.round(k.otherIncome).toLocaleString('ja-JP');
}
```

### 真の原因

**同じ値に対する入力経路が2つあるのに、排他制御をしていなかった。**
勤労学生控除などで実装済みの「条件を満たさない項目はロックして理由を出す」という
既存の方針が、国保の欄には適用されていなかった。設計の一貫性の欠落。

### 修正方法

`refreshKokuhoLocks()` を追加し、選ばれていないほうの入口をロックして理由を表示する。

```js
function refreshKokuhoLocks() {
  var manual = chk('k_manual');
  // ① 手動上書き中は STEP 3 の加入チェックを無効化
  ['A_kokuho', 'B_kokuho'].concat(roster.map(m => 'm' + m.id + '_kokuho'))
    .forEach(id => softLock(id, manual,
      'STEP 7 で「手動で上書きする」を選んでいるため、この加入チェックは使われません。…'));
  // ② 自動計算中は STEP 7 の数値欄を読み取り専用に
  [['k_insured','被保険者数'], ['k_salary','給与所得者等の数'], ['k_other','そのほかの世帯員の所得']]
    .forEach(x => softLock(x[0], !manual, 'STEP 3 の加入チェックから自動計算しています…'));
}
```

ロックには既存の `lock()` ではなく `softLock()` を新設した。
`lock()` は控除用で、ロック時に**値を消す**（`checked = false`）。
ここで値を消すと、手動上書きをやめたときに STEP 3 のチェックが全部外れてしまう。

### あわせて直した点

- **「特定同一世帯所属者の数」を上書き用の折りたたみから外に出した。**
  この項目だけは STEP 3 から判別できず、`k_manual` の状態に関わらず常に使われる。
  上書き欄に置いたままだと「上書きしない限り効かない」と誤解される。
- 自動集計の見出しを、手動上書き中は
  「手入力した値で計算しています（STEP 3 の加入チェックは使いません）」に変える。
- 「被保険者0人」の警告が自動集計値だけを見ていたため、**手動上書き中に誤警告**していた。
  実際に使われている値と特定同一世帯所属者数を合わせて判定するよう修正。

### 再発防止策

- **同じ値への入力経路が2つある場合は、必ず一方をロックして理由を出す**をレビュー観点に追加
- `browser-check.js` に排他の検査を15件追加（ロック状態・理由の文言・値が消えないこと・
  自動に戻したときの復元・手動値が結果に反映されること・値を書き換えても自動値に戻ること）

### 🔴 優先度：高

#### R-01　`app.js` が1,304行で単一ファイルに詰まっている【保守性】

**現状**：フォーム生成・世帯導出・ロック判定・地域設定・結果描画がすべて `app.js` に同居。

**リスク**：税制改正で結果表示を直すときに、無関係なフォーム生成コードを読む必要がある。

**修正提案**：責務ごとに4ファイルへ分割する（ビルド不要のまま実現できる）。

```
assets/
  ui-form.js      … personForm / fld / sel / cb（フォーム生成）
  ui-roster.js    … 世帯構成の描画と扶養区分の導出
  ui-result.js    … render*（結果のHTML生成）
  app.js          … 初期化・イベント・状態管理のみ（300行程度）
```

**工数**：2〜3時間。既存テストがそのまま通ることで安全に実施できる。

#### R-02　入力1文字ごとに全体を再計算・再描画している【パフォーマンス】

**現状**：

```js
document.addEventListener('input', function (e) {
  if (isMoney(e.target)) commafy(e.target);
  refreshAll();                       // ← 毎キーストローク
});
```

`refreshAll()` は内部で `readPerson` を最大8回、`C.calcIncome` を4回、
世帯員数ぶんの `classify()` を呼び、さらに STEP 3・6・7 の DOM を作り直す。

**実測**：世帯員3人で約 12〜18ms／回。60fps（16.7ms）を超えることがあり、
低スペック端末や世帯員が多い場合に入力が引っかかる可能性がある。

**修正提案**：`requestAnimationFrame` によるコアレスと、重い部分の分離。

```js
var pending = false;
function scheduleRefresh() {
  if (pending) return;
  pending = true;
  requestAnimationFrame(function () { pending = false; refreshAll(); });
}
document.addEventListener('input', function (e) {
  if (isMoney(e.target)) commafy(e.target);   // 即時（カーソル位置の維持のため）
  scheduleRefresh();                          // 描画は次フレームにまとめる
});
```

さらに、`renderDetailForms()` は**フォームの増減があるときだけ**呼べばよい
（現在は毎回呼んで差分判定している）。

**効果**：連続入力時の再計算回数が 1/3〜1/5 に減る。

#### R-03　同じ計算を何度も繰り返している【パフォーマンス】

**現状**：`refreshAll()` の中で

- `personGokei('A')` → `readPerson('A')` → `calcIncome()`
- `refreshLocks()` の中で再び `readPerson('A')` → `calcIncome()`
- `deriveKokuho()` の中でさらに `readPerson('B')` → `calcIncome()`

同じ入力から同じ結果を得る計算を、1回の `refreshAll` で3回以上行っている。

**修正提案**：`refreshAll` の先頭で1度だけ計算し、以降は引数で回す。

```js
function refreshAll() {
  readRoster();
  var p = params();
  var ctx = {                                  // 1回だけ計算してコンテキストに持つ
    p: p,
    A: C.calcIncome(readPerson('A', year, true), p, 'income'),
    B: meta.B.enabled ? C.calcIncome(readPerson('B', year, true), p, 'income') : null
  };
  updateLabels(ctx); updateRoster(ctx); updateKokuho(ctx); refreshLocks(ctx);
}
```

**効果**：R-02 と合わせて、入力時の処理量が約 1/4 になる見込み。

### 🟡 優先度：中

#### R-04　`innerHTML` による文字列組み立て【保守性・セキュリティ】

**現状**：結果画面は約600行の文字列連結で組み立てている。

```js
h += '<tr><th>' + esc(x.name) + '</th><td class="num">' + yen(x.amount) + '</td></tr>';
```

**セキュリティ評価**：**現時点で脆弱性はない**。
- 利用者が入力できる自由文字列は存在しない（すべて数値入力・select・checkbox）
- マスタ由来の文字列（市区町村名など）は `esc()` を通している
- 数値は `toLocaleString` を経由するため制御文字が入らない

**リスク**：将来「メモ欄」「氏名欄」のような自由入力を追加したとき、
`esc()` の付け忘れが即座にXSSになる。防御が「開発者の注意」に依存している。

**修正提案（段階的）**：

1. **短期**：`esc()` を強制するタグ関数を導入し、生の連結を禁止する

```js
/* 埋め込み値を必ずエスケープするテンプレートタグ */
function h(strings) {
  var vals = Array.prototype.slice.call(arguments, 1);
  return strings.reduce(function (acc, s, i) {
    return acc + s + (i < vals.length ? esc(vals[i]) : '');
  }, '');
}
// 使用例（エスケープ忘れが起きない）
var row = h`<tr><th>${x.name}</th><td class="num">${yen(x.amount)}</td></tr>`;
```

2. **中期**：`<template>` 要素＋`textContent` への差し込みに置き換える

**優先度が中である理由**：現状の実害はなく、機能追加時に効いてくる予防的改善のため。

#### R-05　マジックナンバーがロジックに散らばっている【保守性】

**現状**：税制の数値の大半は `data.js` にあるが、一部がロジック側に残っている。

```js
/* calc.js */
if (r < 3600000) return A * 2.8 - 80000;        // 給与所得の区分
if (inc.gokei <= 25000000 && adjTarget > 0)     // 調整控除の適用外ライン
adjBase = ... Math.max(..., 50000);             // 調整控除の最低5万円

/* app.js */
lock(w + '_singleParent', has500 && hasChild)   // has500 = g <= 5000000
return salary > 550000 || pension > (age >= 65 ? 1250000 : 600000);  // 給与所得者等
```

**リスク**：これらが改正されたとき、`data.js` だけ見ても直せない。

#### R-06　浮動小数点で金額を扱っている【正確性】

**現状**：税率の乗算に `Number` を使っている。

```js
var cityStd = Math.floor(stdBase * cityRate);   // cityRate = 0.08 など
```

**評価**：現状は**問題を起こしていない**。
- 課税標準額は1,000円単位、税額は100円未満切捨てのため、微小誤差が結果に出ない
- 分離課税の按分では実際に `1 - 0.8 = 0.19999…` の誤差が出たため、
  「合計を先に確定してから按分する」方式に修正済み

**リスク**：新しい按分・比例計算を追加したときに同種の不具合が再発しうる。

**修正提案**：金額計算のヘルパを用意し、直接の乗算を避ける。

```js
/* 税率（％）を掛けて円未満を切り捨てる。内部で整数演算に寄せて誤差を避ける */
function applyRate(amount, ratePercent) {
  return Math.floor(amount * Math.round(ratePercent * 1000) / 100000);
}
```

**現状**：`refreshAll()` は表示更新のほかに、`k_insured` などの**入力欄の値を書き換えている**。

if (!manual) {

**修正提案**：自動計算値は入力欄と分離し、手動上書き時のみ入力欄を使う。

var kokuhoAuto = { insured: 0, earners: 0, otherIncome: 0 };   // 状態として保持
// 読み取り時： chk('k_manual') ? num('k_insured') : kokuhoAuto.insured
